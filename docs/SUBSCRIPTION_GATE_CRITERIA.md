### 撤廃してよいと言える根拠 (「リスクがない」の中身)

1. **REMINDER の derived 誤送信リスクは構造的にゼロ**。C2 の恒久述語 (`estimate_source='flow'` +
   `flow_measured_at` 鮮度 + 窓 `[+3,+7]`) が `listContractsDueForReminder` と**原子 claim の
   両方**に入っている。条件2 が 0 のままでも derived には 1 通も飛ばない。
   → 条件2 は「誤送信を防ぐ壁」ではなく「開けた甲斐があるかの目安」でしかなかった。
2. **MENU の derived 表示は既に誠実**。`subscription-concierge.ts` は `estimate_source` を
   一切読まず、derived も flow も同じ「ごろ」表現になる (下の確認記録)。
3. **条件1 は費用を伴わない**。gate を開けても LINE 到達 4 人に見えるだけで、追加の実費も
   不可逆な公開影響もない (broadcast ではない)。

## 前提: なぜ「開けない」がデフォルトなのか

判断軸は一貫して **「誤送信は回復不能・無送信は回復可能」**。

- 導出 (`estimate_source='derived'`) は「直近注文 + 周期」の推定にすぎず、
  **お届け日変更を原理的に追えない** (タグに現れない)。推定が外れたまま送ると
  「決済済みの顧客に『まもなく決済されます』」級の誤送信になり、取り消せない。
- 実測 (`estimate_source='flow'`、Shopify Flow → `/api/integrations/teiki-flow`) は
  Huckleberry 自身が言う「次回ご注文日」なので、送ってよい唯一の日付ソース。
- したがって **C2 で送信対象は「実測 + 受信 10 日以内」に限定済み** (コード側の恒久述語。
  `packages/db/src/subscription-contracts.ts` の `listContractsDueForReminder`)。
  gate を早く開けても derived 契約に誤送信が飛ぶことはないが、
  「開けたのにほぼ誰にも届かない」状態は運用の混乱を生むため、数値条件を置く。

**現在は 条件3 が `1` であることだけが阻止条件。** 判定は `reminder-dry-run` が毎回出力する
(2026-08-05 の採点で「条件3 は cron-monitor にしか無く dry-run で確認できない」と
指摘されたため、同じサマリで機械判定するようにした)。

⚠️ **判定列を消したのは「嘘をつかないため」**。条件を使わなくなったのに `crit1_...` /
`crit2_...` を出し続けると、読む人はそれを「まだ守っている壁」と誤解する。数値は
`linked_reachable_active` / `measured_active` として**情報列で残す** (Sprint A/C の効果測定に
使う) が、`1/0` の判定は出さない。

⚠️ **`fresh_measured_active` を条件2 と混同しないこと**。これは「今この瞬間に送信資格を持つ
実測」の数で、**周期の大半で小さいのが正常**。トリガー1 は決済 7 日前にしか発火しないため、
前例なし層 (`last_order_at` 欠落・本番 active の約半数) の実測は周期のほとんどの期間
「10 日より古い」状態にある。ここに鮮度を課すと健常時でも過半に届かず、条件2 が永久に
満たされない。鮮度は**送信時**に効かせ、gate 判定では参考値として見る。

- **条件1 が意味していたこと (分母) — 撤廃済み**: 送信可否ではなく「開ける価値」の判定だった。
  分母 30 未満で開けると「開けたのに月に数通」となり効果測定も事故検知もできない、という理屈。
  → **2026-08-11 に撤廃**。理由 = ①開けること自体に実費も不可逆な公開影響もない
  ②分母を動かすのは Sprint A (連携特典 ¥300) と Sprint C (magic-link メール) の仕事であって、
  「橋を閉じておく」ことでは分母は増えない (むしろ MENU が閉じたままだと連携の動機が減る)。
  分母の推移は `linked_reachable_active` を情報列として引き続き追う。
- **条件2 が意味していたこと (カードの信頼性) — リスク実確認へ置換**: MENU を開けると契約カードの
  日付が顧客に見える。derived 過半のまま開けるとカードの日付の大半が推定になり、問い合わせと
  ブランド毀損を生む、という理屈。
  → **2026-08-11 に撤廃**。理由 = 上の「確認記録 ①」のとおり、derived の推定日は**すべて
  「ごろ」+ 脚注**で提示され、出せないときは日付を捏造せず「マイページでご確認ください」に
  畳まれることを実 Flex で確認した。恒久ガード (`sub-intents.test.ts` の §3-2 断定禁止) もある。
  = 「過半が実測になるまで待つ」で守っていたものは、既に**表現側で恒久的に守られている**。
  実測の伸びは `measured_active` を情報列として引き続き追う (Flow 障害の早期発見に有用)。
- **条件3 の意味 (測定器の生存) — 維持**: 実測が止まっていれば実測は腐り始める。
  `estimate_source` を `derived` に戻すのは実注文だけなので、Flow が死んでも行は `flow` のまま
  残り、`measured_active` だけ見ていると「実測は足りている」と誤読する (実際は鮮度述語で送信ゼロ)。
  鮮度述語があるので腐った実測が誤送信になることはないが、**開けたのに 1 通も飛ばない**状態を
  避けるため、受信が生きていることを条件に残す。
  ⚠️ 条件3 は「1 件でも受信があるか」の粗い生存判定なので、**一部トリガーだけの設定ミス**
  (例: スキップ時だけ動いていない) は捕まえられない。契約単位の確認は `contract-diagnose` op で。

条件は**実データで再検討可**。変更する場合は本ファイルと `reminder-dry-run` の判定 SQL の
両方を同時に更新すること (片方だけ変えると判定が嘘になる)。
一致は `apps/worker/src/__tests__/admin-ops-c2-constants.test.ts` が CI で固定する
(撤廃した判定列が**復活していないこと**も含めて検査する)。

## C2 の送信述語 (コード側の恒久ガード・gate とは独立)

gate が開いた後も、送信は常に次の全てを満たす契約に限られる:

- `estimate_source = 'flow'` (実測のみ。derived は永久に送らない)
- `flow_measured_at` が **10 日以内** (`FLOW_MEASUREMENT_FRESH_DAYS`)。
  前サイクルの実測の取り残し (「お届け日変更 + 7日前通知」の両 Flow 喪失) を落とす。
  10 の根拠: トリガー1 は決済 7 日前発火 → 窓下限 (3 日前) でも受信 4 日後 = 余裕 2 倍強。
  前サイクルの実測は最短周期 20 日でも 13 日以上前 = 確実に落ちる。
  ⚠️ Huckleberry の「注文前確認メール」の日数 (現在 7) を 13 日超にするとここも要見直し
- 未解約・未一時停止・同一推定日で未送信 (従来どおり)
- 送信直前の再導出検算 (staleEstimate) と実測限定の関門 (notMeasured) を通過 (#229 A-1 系譜)
