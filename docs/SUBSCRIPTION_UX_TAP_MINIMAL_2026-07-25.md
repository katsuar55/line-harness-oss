# サブスク操作 UX タップ最小化 — 最終設計 (2026-07-25)

22 エージェントのワークフロー (設計 4 案 → 3 視点審査 → 統合 → 6 次元採点) の成果を、
審査員が指摘した致命傷を潰した上で再統合したもの。**自動統合版は採点で不合格 (trust 24 / migration-safety 23)
だったため破棄し、審査で 80-88 点を得た 4 案の「良点」と「fatalFlaws」を根拠に本書を作り直した。**

## 0. 結論 (現行設計 docs/SUBSCRIPTION_REMINDER_AND_WIZARD_2026-07-24.md 第2部 から何を変えるか)

| # | 変更 | 理由 |

## 1. 背骨: 受理レイヤー (sub_intents)

```
顧客のタップ = 「意思の受理」であって「実行」ではない。
  ① 受理 (INSERT sub_intents)  ← ここまでが 1 タップ。
      対応する op が定義されたタップは常に成功する (op が存在しない要望は §2 ※2 のとおりカードに出さない)
  ② 実行 executor で分岐
       human        … 移行前 (スタッフが Huckleberry 管理画面で代行。★代行可否は未検証 — §11)
       own_billing  … 移行後 (自社課金の mutation)
       blocked      … 移行窓 (受理はする。実行だけしない。窓明けに再評価)
       api          … ★Huckleberry API 連携が通れば移行前でも自動実行 (要問い合わせ)
  ③ 完了 or 正直な失敗を必ず通知
```

`sub_intents` (migration 074 想定):
```
id
friend_id
contract_ns              -- 'hb' | 'own'  ★移行境界を跨ぐので名前空間が必須
contract_key             -- ns='hb' → huckleberry_contract_id / ns='own' → own_contract_gid
target_cycle_key         -- ★提示時のサイクル識別子 (契約 + 想定決済日)。古い吹き出し対策の要
presented_scheduled_date -- ★提示時に画面へ出した予定日。受理時に現在値と突合する
op(skip|date|pause|resume|cancel|undo_of)
state(received|executing|done|expired|failed|cancel_requested|cancelled|deferred|superseded)
requested_by(customer|staff|system)   -- 種別
actor_staff_id / actor_role           -- ★個人。受理・実行・却下の各遷移で記録 (staff_members 参照)
payload_json / deadline_at / promised_by / claimed_at
created_at / resolved_at / executor / supersedes_intent_id
```

### 1-1. 一意性 (二重タップを型で潰す)
```sql
CREATE UNIQUE INDEX ux_sub_intents_open
  ON sub_intents(contract_ns, contract_key, target_cycle_key, op)
  WHERE state IN ('received','executing','deferred');
```
受理は `INSERT ... ON CONFLICT DO NOTHING`。0 行なら**新規作成せず既存 intent の状況カードを返す**
(= 二重タップは冪等に「承り済みです」)。リポジトリ既存の CAS 規律 (referral の `UNIQUE(reward_id)`、
リマインドの claim、`sub-link.ts` の `consumed_at` CAS) と同型にする。**唯一 CAS を持たない台帳を作らない。**

### 1-2. state 機械 (op 別の terminal 規則)
| op | 締切超過時 | 理由 |
|---|---|---|
| `skip` / `date` | `expired` 可 (§4-2 で正直に通知) | 当該サイクル限りの操作 |
| `pause` / `cancel` | **`expired` 禁止**。`received` のまま保持し次サイクルへ自動繰越し + エスカレーション | 解約意思を期限切れで無効化するのは特商法上の解約妨害。§4 第4層で救済する |
| `undo_of` | 逆操作なので元 intent の state に従属 | — |

- **繰越しの実体**: `pause` / `cancel` の締切超過は、**同一行の `target_cycle_key` と `deadline_at` を次サイクルへ
  UPDATE する**ことで繰り越す (新規 INSERT しない = §1-1 の partial UNIQUE と衝突しない)。
  これを書かないと §4-2 の締切超過 sweep 述語 (`state='received' AND deadline_at < now`) に**毎 run 再ヒットし続け**、
  エスカレーションが無限に鳴る。エスカレーション通知は **1 intent 1 回**に制限する (§4-2 の約束破り通知と同じ抑止)。
- `executing` は **claim**。`claimed_at` を持つ。**30 分超過の自動解放は機械 executor (`own_billing` / `api`) 限定**とし、
  解放回数を可視化する。sweep 対象は `state='received'` のみ (executing は解放後に拾う)。これで機械側の silent limbo と誤 expire の両方を消す。
- **`executor='human'` の `executing` は自動解放しない。** 人間は HB 管理画面という system 外で不可逆操作を行うため、
  解放 → 再 claim が **二重実行** (二重 skip / 二重解約) を生む。しかも §4-3 の skip 照合は「タグ付き注文が出ないこと」
  なので**二重 skip を `ok` と誤判定**し、機械検出をすり抜ける (→ §4-3 で照合条件を強化する)。
  30 分超過は**アラートのみ**を上げ、state は `executing` のまま**人間が解決する**。
  silent limbo に落とさないため、**未解決時間 (now − `claimed_at`) を `/admin/ops` に常時可視化**し、超過分は一覧の先頭に固定する。
- **`executing → done` の CAS が 0 行だったら「完了」と表示しない。** state を `executing` のまま保持して
  UI / 通知は**「確認中」**に落とし、Discord alert を上げる。0 行は「別 claim が既に触った」= 二重実行の疑いなので握り潰さない。
  (§1-3 が undo について定めた「**0 行なら成功と言わない**」を、実行側にも同一適用する。)
- `executor='blocked'` の行は **`deferred`** に置き、§4-2 の sweep 述語から除外する (`executor <> 'blocked'`)。

### 1-3. undo は state で決める (時刻で決めない)
- `[取り消す]` は必ず CAS:
  `UPDATE sub_intents SET state='cancelled' WHERE id=? AND state IN ('received','deferred')`。
  **0 行なら「取り消しました」と言わない。**
  (`deferred` を含めるのは、移行窓で受理だけした意思 (§5-1) を顧客が取り消せなくなるのを防ぐため。
  `deferred` は「未実行」であって「実行中」ではないので、`received` と同じ扱いでよい。)
- `executing` / `done` に対する undo は**新しい intent** (`op='undo_of'`, `supersedes_intent_id`) として受理し、
  UI は「**取り消しのご依頼を承りました**」止まりにする (受理と実行を分ける §1 の規律を undo にも同一適用)。
- したがって undo 可能期限は時刻ではなく **「スタッフ着手前まで」**。時刻を表示するなら
  executor 側に**同じ長さの着手ホールド**を課す (§4)。両者が一致しない表示はしない。

### 1-4. その他
- **`requested_by` で「顧客が意図した pause」と「決済失敗による自動 pause」を分離**する。
  `subscription-concierge.ts:191` のコメントどおり Huckleberry の pause タグは原因を運ばないため、
  これが無いとリカバリ通知が誤発火する (案4 の固有の良点)。
- **`requested_by` は種別、`actor_staff_id` は個人**。共有 env API_KEY (`env-owner`) での代行実行は**禁止**。
  既存の `staff_members` / `getStaffByApiKey` / `requireRole` / `auditAdminAction` / `/admin/logs` に必ず載せる
  (コミット `4f3e6f2` のスタッフ個別アカウント化から退行させない)。監査 metadata は `contract_key` と `op` のみ (PII を残さない)。
- state が `done` になるまで UI は「承りました」しか言えない。**false-success を運用ルールでなく型で防ぐ**。
- **台帳は sub_intents に一本化する。** `sub_migration_snapshots.pending_intent` は sub_intents への参照
  (`intent_id`) を持つ射影に降格させる (§5)。二重台帳は「解約済み顧客に『お手続きできませんでした』」を生む。

※2 移行前の「1タップで決済日を1週ずらす」は**成立しない**。対応する op が定義できないので
**ボタン自体をカードに出さない** (出した上で受理を拒む = §1 の「受理は常に成功する」を破る、をしない)。HB は決済失敗で自動一時停止し、
`computeNextBillingEstimate` (`subscription-contracts.ts:174-182`) は停止中の契約に `null` を返す
= ずらす先の日付が存在しない。そもそも主要因 (カード失効・限度額) は日付移動で解決せず、

移行前は `buildPaymentRecoveryMessages` と同じく**原因を断定せず**マイページ導線に留め、
「1タップ復旧」は `executor='own_billing'` (PHASE3 §6.4 の `customer_payment_methods` 経路) 以降として §10 の Phase 3 待ちへ置く。
決済失敗カードには `[お支払い方法を確認する]` を必ず併記する (会員登録が必要な旨を事前開示)。

**初回連携の友だち追加は LIFF「友だち追加オプション」で LINE ネイティブ画面に畳む。
採用値 = On (aggressive)** (2026-07-26 決定・§10-2 注記参照。本書の初版は On(normal) =
「aggressive は画面が増えるので使わない」としていたが、**タップ数よりも完遂率を優先して反転**した)。
理由: 友だち追加は redeem の必須条件 (friend 行が無いと preview 404) なのに、normal の同意画面
チェックボックスは**見落とすと追加されないまま LIFF が開き、404 リトライ待ちに落ちる**。
aggressive の専用 1 画面 (+1 画面) はこの脱落経路を塞ぎ、既存友だちには表示されない = 追加コストは
未友だち (まさに magic-link の対象) だけが払う。
**畳めるのは友だち追加の独立タップだけで、権限同意画面そのものは残る** (初回のみ)。
到達 3/112 のボトルネックはこのフローなので、離脱見積りを楽観方向へずらさないため 1+1 と書かない。

## 3. undo 型 1 タップを正当化する唯一の条件

> **確認画面に出すはずだった情報を、押す前に読める位置へ繰り上げる。
> ただし繰り上げ先は「ボタンのラベル」ではなく「ボタン直上の本文行」。**

```
✗  [ 今回はお休み ]            → 確認画面 → [ はい ]
✗  [ 今回はお休み → 次は9月4日ごろ ]   ← ラベルは単行・切詰め。実機で「…次は9月…」と日付が消える
✓  押すと 次回は 9月4日ごろ になります      ← text / wrap:true / size:'xl' / bold / #0f766e
   [ 今回はお休み ]                         ← button ラベルは全角8字以内の動詞句
```

### 3-1. ラベル制約は「40 字」ではなく「描画幅」
`action.label` の 40 字は **API のデータ上限であって描画幅ではない**。既存カードは
`subscription-concierge.ts` の `buildContractBubble` / `buildGuideBubble` がすべて `size:'kilo'`
(幅 260px / `paddingAll:16` → ボタン内幅 約 228px)。button の label は**単一行・折返し不可・末尾から省略記号で切詰め**、
フォントサイズも文字色も指定できない (`primaryButton` が渡せるのは `style` / `height` / 背景 `color` のみ)。
全角は概ね 14〜15 字で打ち止めなので、「今回はお休み → 次は9月4日ごろ」は
**まさに繰り上げた実日付から先に消える**。40 字チェックは通るのでレビューでも本番投入まで気づけない。

したがって:
- **ボタンラベルは全角 8 字以内の動詞句**に固定する (例「今回はお休み」「日付を変える」)。
- **結果 (日付) は独立した `text` 行**に置き、`wrap:true` / `size:'xl'` / `weight:'bold'` / `color:'#0f766e'` を効かせる。
  §7 の可読性トークンと両立できるのはこの形だけ (ラベルにはサイズも色も効かない)。
- どうしてもラベル内に結果を入れるなら、`box` + `action` の **tappable box** 化して内部 `text` を 2 行
  (1 行目=操作名 / 2 行目=結果日付) にする。`size:'giga'` (386px) への変更は**上限が伸びるだけで「切れない保証」にはならない**
  (実効上限は端末幅・フォント設定に依存する)。どの `size` でもラベルは全角 8 字以内に固定し、下記受入条件で確認する。
- **受入条件**: 「40 字以内であること」ではなく、**最長ケース (プラン名込み・2 桁月日) を
  実機または Flex Message Simulator の 320px 幅で表示して切れないこと**を検証する。

### 3-2. 日付は推定である — 断定表示の条件を限定する
`next_billing_estimate` は「直近注文日 + 周期 × (1+skip差分)」の**推定**で、HB のお届け日変更はタグに現れない
(`subscription-contracts.ts:12-15`)。既存 UI が「ごろ」を義務化しているのはこのため。

| `estimate_source` | 表示 | 締切表示 |
|---|---|---|
| `derived` (タグ由来の推定) | **必ず「◯月◯日ごろ」**。断定しない | 保守側に丸める (実締切より手前) |
| `flow` (Shopify Flow で実測受信済み / `docs/TEIKI_FLOW_SETUP.md`) | 実日付の断定可 | 実日付 |

- **`flow` 以外で断定日付を出さない。** 「変更は8月6日まで」と太字で断定して実際は 8/9 まで有効、
  という表示は顧客に諦めさせる = §4 の誠実さに正面から反する。
- 移行前 (`executor <> 'own_billing'`) は結果断定を避け、**申込であることが読める語**にする。
  例: 「押すと **9月4日ごろ** のお届けに変わるお申し込みになります」。
  実行後カードは `done` まで「承りました (反映予定: ◯日)」、`done` 後に確定日付へ差し替える**二段表示**。
- **前提作業**: TEIKI_FLOW の各トリガー (契約作成 / スキップ / お届け日変更) の設定を §10「今すぐ」に含める。

### 3-3. 古い吹き出し対策 (nonce を先出ししない代わりに必ず要る)
LINE の吹き出しは消えない。§9 で `st=go` nonce の先出しを却下している以上、**サイクル束縛が唯一の防壁**になる
(07-24 設計 `SUBSCRIPTION_REMINDER_AND_WIZARD_2026-07-24.md` の `y=<cycle_index>` / `L4 サイクル整合` を書き戻す)。

- postback に **`y`(target_cycle_key) と `d0`(presented_scheduled_date)、`v`(スキーマ版)** を載せる。
- **受理ハンドラ冒頭で必ず最新値を再取得する** (経過日数による分岐を設けない — 「N 日超だけ再取得」は
  再取得しなかった側が古い値のまま INSERT される穴になる)。突合結果ごとの結末は**1 つに固定する**:

  | 突合結果 | 結末 |
  |---|---|
  | `y` ≠ 現在サイクル / `v` が旧版 | **INSERT せず**「このご案内は期限切れです。最新のご契約はこちら」 (対象サイクルが既に過ぎている = 受理しても実行先が無い) |
  | `y` は一致・`d0` ≠ 現在予定日 | **INSERT せず**、最新予定日を出した**確認へフォールバック** (同一サイクル内の推定日ズレなので意思はまだ有効。期限切れ扱いにして諦めさせない) |
  | 一致 | 受理 (§1-1 の partial UNIQUE を通す) |
- 受理レベルの単回性は §1-1 の partial UNIQUE が担保する (同じ吹き出しの再タップで意思が積み上がらない)。

### 3-4. undo
- 実行後カードに **[取り消す]** を必ず併記する。**期限は時刻ではなく state で示す**
  (「スタッフ着手前まで取り消せます」)。CAS と `undo_of` の扱いは §1-3。
- **60代は undo に気づけない**ことを前提に、「押す前に結果が読める」ことで守る。これが省略との差。
- **撤退基準**: undo 実行率が skip 実行の 10% を超えたら 1 タップを取り下げて確認型へ戻す (数値で先に置く)。

### confirm を維持するもの (可逆性グレード)
| 操作 | 判定 | 確認 |
|---|---|---|
| **初回連携** | ③第三者被害 — 転送リンク/共有端末で他人の LINE に紐付くと **single-use トークンなので本人が二度と連携できない** (`services/sub-link.ts` の consumed_at CAS + UNIQUE index の仕様どおり) | **維持** |
| 解約 | ①不可逆 | 維持 (2タップ) |
| skip / 日付 / 一時停止 | 可逆 | **undo 型 1 タップ** |

## 4. 誠実な失敗 — 代行を出荷可能にする 3 層 + 第0層 (再評価) と第4層 (`cancel` 救済)

(これが無い代行は壊れたマイページより悪い。以下 0〜4 の 5 項目すべてが出荷条件。
「3 層」は中核 1〜3 を指す呼称であり、0 と 4 を省いてよいという意味ではない。)

**0. 実行の直前に締切とサイクルを再評価する (提示時の評価だけでは足りない)**
   - executor は実行直前に必ず (i) `deadline_at` の再評価 (ii) 対象サイクル
     (`contract_ns`+`contract_key`+`target_cycle_key`) の再取得 を行う。
     どちらかがズレていたら**実行せず** `failed(reason='deadline_passed' | 'cycle_drift')` にして正直に通知する。
   - `/admin/ops` の実行ボタンは CAS を通ってからのみ活性化する:
     `UPDATE sub_intents SET state='executing', claimed_at=now, actor_staff_id=? WHERE id=? AND state='received'`
     — **`op IN ('skip','date')` のときのみ `AND deadline_at > now` を付ける**。
     cron の expire と**同じ述語**で相互排他にし、`expired` 済みの行にはボタンを出さない
     (「失敗通知の 3 分後にスタッフが done を押す」を構造的に不可能にする)。
   - **`pause` / `cancel` に `deadline_at > now` を付けない**のは §1-2 (expire 禁止・繰越し) と §4 第4層 (締切跨ぎの
     キャンセル/返金救済) を成立させるため。締切条件を全 op 一律にすると、救済すべき解約が管理画面から実行不能になる。
   - **★例外: 移行窓で受理した `deferred` 意思には「窓明け再アンカリング」を先に適用する (→ §5-4)。**
     窓中に受理した意思は HB 期の `target_cycle_key` と**既に過去化した `deadline_at`** を持つ。
     これを素のまま第0層に掛けると `cycle_drift` / `deadline_passed` で **100% 弾かれ**、
     §5 の存在理由 (「意思を捨てると休みたかった回が即日課金される」) が**自らのガードで消える**。したがって:
     ① `deferred → received` へ戻す遷移では **`deadline_at > now` の CAS 検査を免除する**
     (遅延は当社都合であって顧客の遅刻ではない)。
     ② 第0層の再評価は **§5-4 で再アンカーした後の新しい `target_cycle_key` / `deadline_at`** に対して行う。
     **再アンカー前の値で第0層を評価しないこと。** 再アンカー後もなお実行不能な場合の結末 (failed にせず顧客に選ばせる)
     と、再アンカー自体が失敗した場合の通知義務も §5-4 に従う。

**1. 受理した瞬間に所要時間を約束する — ただし `promised_by > deadline_at` を先に潰す**
   - **順序**: ① 営業カレンダーから `promised_by` を算出 → ② `promised_by` と `deadline_at` を比較 →
     ③ `promised_by > deadline_at` なら**「今回は間に合いません」を受理前に開示**し、受理するか顧客に選ばせる。
   - **24h という固定閾値は補助表示に降格する。開示の判定式は本書全体でこの `promised_by > deadline_at` 1 つだけ**
     (§2 ※1 もこの定義に従う)。24h だけで判定すると、金曜 20:00 / 日曜締切 (残 52h) の契約が
     「翌営業日のお昼まで」= 月曜 = **締切超過**を約束してしまう。84 契約 × 週末の確率で毎サイクル構造的に起きる。
   - 比較は受理時の**必須バリデーション**に置く (`deadline_at` / `promised_by` は §1 のスキーマに既にある)。
   - **モードB (移行窓) の promised_by は営業時間ベースで出さない。**
     「お切り替え完了後 (◯月◯日ごろ) に反映します」に差し替える (実行は最速でも `billing_aligned`+48h 後のため)。

**2. 期限監視は二段 sweep にする**
   | sweep | 述語 | 動作 |
   |---|---|---|
   | 約束破り | `state='received' AND promised_by < now AND executor <> 'blocked'` | 顧客へ「お時間をいただいています」(**1 intent 1 回のみ**) + Discord alert |
   | 締切超過 | `state='received' AND deadline_at < now AND executor <> 'blocked'` | `op` 別 terminal 規則 (§1-2) を適用。`skip`/`date` は `expired` + 正直な失敗通知、`pause`/`cancel` は expire せず**同一行の `target_cycle_key` / `deadline_at` を次サイクルへ UPDATE (= 繰越し)** + エスカレーション (1 intent 1 回) |
   - `executing` は sweep 対象外 (30 分の claim timeout で `received` へ解放されてから拾う)。
   - **繰越しで `deadline_at` を前進させないと、`pause`/`cancel` が締切超過述語に毎 run 再ヒットして
     エスカレーションが鳴り続ける。** 述語と §1-2 の terminal 規則はこの UPDATE でのみ整合する。
   - `executor='blocked'` の除外を落とすと、**移行窓中の解約意思が expired で消える**か、
     「間に合いませんでした」と通知した後に PHASE3 側が実行する矛盾が起きる。

**3. 実行漏れを機械検出する — op 別に、窓で、第3値ありで**
   | op | 照合条件 | 窓 |
   |---|---|---|
   | `skip` | ① `subscription-id:{ID}` タグ付き注文が**出ないこと** (`parseOrderSubscriptionTags`) **かつ** ② **次回課金予定日がちょうど 1 サイクル分だけ進んだこと** (①だけでは二重 skip を `ok` と誤判定する) | 推定日 −2〜+7 日。`estimate_source='derived'` は −3〜+7 日に広げる |
   | `date` | 注文が**新予定日側にのみ**出ること | 旧予定日/新予定日の両方を監視 |
   | `pause` / `cancel` | 以後の注文が**出ないこと** | 次サイクル 1 周期分 |
   - **1 点判定にしない。** 「決済予定日の翌日」だけを見ると、実決済が推定より後ろにズレた契約で
     「まだ注文が無い = 正常」と誤判定して代行漏れを取りこぼす。skip は
     「`last_order_at` が受理時点から進む」か「推定日 + 周期の半分を経過」するまで open のまま監視し、
     注文が出現した時点で即アラート。
   - **skip を「注文が出ないこと」だけで判定しない。** 注文の不在は 1 回 skip でも 2 回 skip でも同じに見えるため、
     §1-2 の human claim 二重実行 (自動解放 → 再 claim) を素通りさせる。**次回課金予定日の前進量が 1 サイクル分ちょうど**
     であることを必ず併せて検証し、**2 サイクル分進んでいたら `miss` (二重 skip)** として下記の検出アクションに載せる
     (顧客は「1 回休むつもりが 2 回止まった」= 顧客不利益方向なので、返金ではなく次回分の前倒し是正を人間が判断する)。
     前進量の測定は `estimate_source='flow'` を前提とし、`derived` で誤差が周期の半分を超える場合は `判定保留`。
   - 判定は **`ok` / `miss` / `判定保留`** の 3 値。窓内不定は保留にして誤検知を出さない。
   - **検出時のアクション**: ① 顧客へ謝罪 + 是正案内 (transactional なので §8 の頻度制御対象外)
     ② Discord alert ③ 返金 / 再送の判断は人間。ここまで書いて初めて「機械が気づく」が顧客に届く。

**4. `cancel` は期限切れにしない — 救済まで書く**
   - `cancel` intent が締切 24h 前に未実行なら Discord / 担当者へ**強制エスカレーション**。
     この 24h は**エスカレーション閾値**であり、§4-1 の開示判定 (`promised_by > deadline_at`) とは別物。混同しない。
   - 締切を跨いだ場合は**当該サイクルの注文をキャンセルまたは返金する**。
   - この救済手順を**受理時の文言にも入れる** (「間に合わなかった場合は必ずご連絡し、
     すでに発送済みのときは返金でご対応します」)。

**代行の監査 (これが無い代行は運用に載せない)**
- 受理 / 実行 / 却下 / expire の**全遷移**で `auditAdminAction` を呼ぶ (`targetType='sub_intent'`)。
- `/api/admin/sub-intents/*` は `requireRole('owner','admin')` を明示。
  **共有 env API_KEY (`env-owner`) での代行実行は禁止**、個人キーのみ。
- 受入条件: `/admin/logs` から**契約単位で「誰がいつ何をしたか」を追跡できる**こと。

→ SLA という「人の善意」に顧客体験を預けない。3 層目が案2 が他案に勝った決定打。

## 5. ★移行窓 (モードB) は代行「実行」も禁止 — ただし受理は必ずする

`docs/PHASE3_BILLING_DESIGN_2026-07-19.md` §7.0 は移行窓の skip / 日付 / 再開を**ブロック**する設計で、
§7 `billing_aligned` の差分検査は**承継課金日を基準値として確定**する。

> **窓中にスタッフが Huckleberry 管理画面で skip / 日付変更を代行すると基準値が動き、phase hold か
> 二重加算判定を誘発する = 移行機械と正面衝突する。**

**衝突するのは「実行」であって「受理」ではない。** 受理まで止めると台帳に行が残らず、
PHASE3 §7 `activated` の遅延 catch-up (`scheduleEdit(当該 cycle → 本日)`) が**休みたかった回をそのまま即日課金**する。
顧客は再タップの機会すら与えられない。したがって §1 の `executor='blocked'` の定義 (「意思だけ台帳に残す」) が正であり、
本節はそれに従う。

### 5-1. 受理と実行の分離
- **skip / 日付 / 再開も必ず受理する** — `INSERT sub_intents (executor='blocked', state='deferred')`。
  実行のみ禁止。返す文言は「承りました。お切り替え手続きの都合で反映は◯日以降になります」
  (「数日お待ちください」で突き放さない)。
- **pause / cancel も同じ台帳に受理する。** `sub_migration_snapshots.pending_intent` は
  **sub_intents への参照 (`intent_id`) を持つ射影**に降格する (単一 TEXT 列の後勝ちで解約が pause に化けるのを防ぐ)。
- 上書き規則: **`cancel` は `pause` を上書きできる。`pause` は `cancel` を上書きできない**
  (解約の取り消しは有人のみ)。上書きが起きたら旧 intent を `superseded` にし、
  **現在の受理状態を 1 通に畳んで必ず再提示**する。

### 5-2. 窓の開始境界は `snapshotted` へ前倒しする
承継課金日の基準値は **`snapshotted` の時点で確定**する。`own_created_paused` から凍結を始めると、
`pending_card` レーン (支払方法 0 件 → 依頼 → PHASE3 §6.4 で自動復帰) の**数日〜無期限の滞留中**に
代行が入り、陳腐化した基準値で契約が作られ、`billing_aligned` の差分検査が必ず不一致になる
(自己修復はするが、112 契約規模では phase hold + Katsu 承認が大量発生して運用が破綻する)。

- **凍結範囲 = `snapshotted` 〜 `billing_aligned`。凍結するのは「実行」だけ** — 代行実行も自社課金 mutation も止める。
  **顧客のタップ (受理) は凍結しない** (§5-1 のとおり `executor='blocked' / state='deferred'` で必ず台帳に残す)。
  「顧客操作も凍結」と書くと §5-1 と正面衝突するので、この区別を落とさないこと。
- **凍結できるのは harness を経由する実行だけ**である。顧客が Huckleberry のマイページから
  自分で skip / 解約する経路は**こちらから凍結する手段が無い** (基準値が動きうる)。
  検知・是正の要否は §11 の未解決に置く。
- **どうしても代行が必要な場合の逃げ道は phase で二分する** (`PHASE3_BILLING_DESIGN_2026-07-19.md` §7.2 に従う。
  「逃げ道はこれ一本」と一本化してはならない):

  | phase | 逃げ道 |
  |---|---|
  | **`own_created_paused` 以前** | **snapshot を破棄して `rolled_back` → 再 snapshot** (PHASE3 §7.2「own_created_paused 以前: own cancel のみ」) |
  | **`hb_stop_requested` 以降** | **rollback 禁止・前進のみ。** 障害時は **billing-kill + 手動請求 runbook** (PHASE3 §7.2 / §8。下書き注文請求時は当該 cycle_key の claim を手動 succeeded 化 + order_id 記録 + 次サイクル `scheduleEdit` を必須手順化) |

  `hb_stop_requested` 以降で `rolled_back` すると、HB 契約は既に停止方向へ動いているのに own 契約は
  **cancel + gid クリア**されるため、**顧客が HB 側も own 側も契約を持たない無契約状態**になる (サイレントな契約消失)。
  PHASE3 §7.2 の文言は境界を `huckleberry_stopped 以後` と書いているが、**停止宣言 (`hb_stop_requested`) の時点で
  HB 側は既に不可逆方向へ動いている**ため、本書は保守側に倒して `hb_stop_requested` を禁止開始点とする
  (この 1 phase 分の差分の是非は §11 の未解決)。
- `pending_card` 復帰時は §7 の「次回決済日まで 5 日以上」検査と**snapshot 再取得**をセットで再実行する (運用 SOP)。

### 5-3. gate は env を廃するのではなく AND する
```
実行可否 = SELF_BILLING_ENABLED
         ∧ phase ∉ [snapshotted … billing_aligned]     (契約単位)
         ∧ ¬quarantine (own_billing_quarantine に無い)
         ∧ ¬breaker_tripped (サーキットブレーカー / billing-kill)
```
- `canIssueAttempt` (PHASE3 §8) は attempt 発行のガードであって**顧客起点の `scheduleEdit` を覆わない**。
  breaker trip 中・billing-kill 中に顧客タップが cadence を動かすと、§8 の解除 runbook
  (バックログを `scheduleEdit` で分散) と競合する。
- §7③ の HB 由来 Order 遅延で `own_billing_quarantine` へ隔離された契約は `phase='activated'` のままなので、
  **phase だけを見ると返金判断中の契約に顧客操作が通る**。
- **kill / breaker 作動中の縮退規則** (07-24 設計から引き継ぐ):
  縮退するのは**実行**であって受理ではない (§5-1 と同じ規律)。**全 op を受理し続ける**。
  ただし `skip` / `date` は **`deferred` に置き、反映時期が読めない旨を明示した上でマイページ導線を併記**する
  (「承りました」だけで放置しない)。`pause` / `cancel` は受理した上でエスカレーション対象に載せる。
  ※ここで「skip / 日付変更は受理しない」と書くと §1 の背骨と §5-1 に矛盾するため、そうは書かない。

### 5-4. 窓の出入りでの結線 (これが無いと false-pending が残る)
- **窓入場前**: 未実行の `cancel` intent があれば `snapshotted` へ入れず、**先に実行する**。
- **`activated` step の順序**: 「pending intent 実行 → **sub_intents を `done` へ CAS 更新 + 完了通知を発火** → phase 確定」。
  crash-resume は phase 未確定で再実行できる。この結線が無いと、own 側は解約済みなのに
  sub_intents は `received` のまま残り、LIFF は永久に「承りました」を表示し、§4-3 が鳴り続ける。
- **catch-up の直前に deferred 意思を評価する**: 当該契約に `deferred` な skip があれば
  `scheduleEdit(skip)` + 次アンカーへ回し、**即日課金しない**。実行不能なら
  「窓中のご依頼は反映できませんでした。今回分は◯月◯日に課金されます」を**課金前に**必ず通知する。
- **名前空間の付け替え**: `activated` 時に当該顧客の未解決 intent の `(contract_ns, contract_key)` を
  `('hb', huckleberry_contract_id)` → `('own', own_contract_gid)` へ書き換える。
  ゲート引き当ては ns に応じて `huckleberry_contract_id` / `own_contract_gid` の**両方向**を引く
  (これを書かないと gid で来た key を HB 列で検索して 0 件 → モードA 扱いで代行実行、という取り違えが起きる)。
- **★窓明け再アンカリング (付け替えと同一トランザクションで行う。→ §4 第0層)**:
  ns だけ付け替えて cycle / 締切を HB 期のまま残すと、§4 第0層の実行直前再評価が
  `cycle_drift` / `deadline_passed` で**受理済みの意思を 100% 弾き**、本節の存在理由
  (「意思を捨てると休みたかった回が即日課金される」) が**自らのガードで消える**。したがって:
  - **上記の `(contract_ns, contract_key)` UPDATE と同一トランザクションで**、`target_cycle_key` を
    **own 側の次サイクル識別子**へ、`deadline_at` を **own 側の新しい締切**へ**再計算して書き換える**。
  - **意思は「どのサイクルか」ではなく「次に課金される回」に再アンカーする。** 顧客が押したのは
    特定のサイクル ID ではなく「**次に来る課金**を休む / ずらす」なので、窓で遅れた分は own 側の
    次に課金される回へ載せ替えるのが意思に忠実。
  - **`deferred → received` へ戻す際は `deadline_at > now` の CAS 検査を免除する**
    (遅延は当社都合であって顧客の遅刻ではない)。**評価は再アンカー後の新しい締切で行う** (§4 第0層と同一規則)。
  - **再アンカーの結果その op がもはや意味を持たない場合** (例: 対象サイクルが既に課金済み / 出荷済み) は、
    **`failed` にしない。**「**次回分へ繰り越す**」か「**今回のご依頼を取り消す**」かを顧客に 1 タップで選ばせる
    (諦めさせない側に倒す。§1-2 の `pause`/`cancel` 繰越しと同じ思想)。返答があるまで `deferred` のまま保持し、
    §4-2 の締切超過 sweep からは除外し続ける (放置に見えないよう §4-2 と同じく 1 intent 1 回の督促は出す)。
  - **再アンカー自体が失敗したら課金前に正直に通知する** (上の「実行不能なら…課金前に必ず通知」を維持。
    再アンカー失敗を無言で `failed` にして終わらせない)。

## 6. 到達 (3/112) — 変換率と混同しない

`?slk=` fast path は**到達した人の変換率**を上げるだけで、到達そのものは 1 件も増やさない。到達は三重化で解く。

**前提: `?slk=` トークンは経路によって「載る／載らない」が違う。** ここを混ぜると
「fast path を実装したのにトークンが来る母集団が 0」という出荷になる。

| # | 経路 | トークン | 前提作業 |
|---|---|---|---|
| **0** | **生成バッチを店舗側メールで差し込み送信** (`generateSubLinkBatch` の entries: email / 氏名 / プラン / link) | **個別 `?slk=` あり** | バッチ生成 + 送信手段。**§10-1 の fast path が効くのはこの経路だけ** |
| 1 | Huckleberry「注文前の確認メール」への相乗り — 唯一いま 112 名全員に届く経路 (2026-07-25 に 7 日前へ修正済) | **なし** (HB テンプレートは HB の差し込み変数しか扱えない) | **静的 LIFF リンク + セルフ連携** (email OTP: `services/account-link.ts`)。`ACCOUNT_LINK_ENABLED` は既定 off、自前ドメイン送信も未対応 → **両方を §10「今すぐ」の前提として実施する** |
| 2 | 発送 webhook 起点の自前ドメイン transactional メール | 個別 `?slk=` あり | 独自ドメイン送信設定 (未対応・最大レバー) |
| 3 | 同梱チラシの個別 QR — オフライン層 | 個別 `?slk=` あり | **紙専用の TTL と第2要素** (下記 6-3) |

### 6-3. 紙経路 (QR) は email 経路と同じ TTL を使わない
`sub-link.ts` の既定 TTL は 30 日 (最大 90 日)。紙に印刷すると、そのトークンは数週間〜3ヶ月
**物理的に読み取り可能なまま顧客宅と廃棄経路に残る**。email 経路の安全性は
「受信箱に届いた事実が email 所有の証明」という前提 (`sub-link.ts` 冒頭コメント) に立つが、**紙にはこの前提が無い**。
同居家族が先に読むと single-use CAS で本人が二度と連携できず、第三者にプラン名と契約操作 UI が渡る。

- 紙用 batch を分離し、`generateSubLinkBatch` の `expiresInDays` を**明示指定 (発送日から 14 日)**。
- redeem 時に**第2要素を 1 つ要求**する (注文番号 または 登録メール下4桁)。
- 最低限「**紙経路は既定 TTL を使わない**」を実装の受入条件にする。

### 6-4. `?slk=` の sessionStorage 退避 (削除条件まで書く)
現行 `liff-pages.ts` の `checkSubLinkParam` は `replaceState` で URL から即削除する。これは
履歴・共有スクショへの残留防止という**意図的な防御**なので、退避は**同一セッションのリロード救済に限る**と目的を限定する。

- 退避キーは **`friendId` (または liff idToken の `sub`) でスコープ**する
  (共有端末で別の LINE アカウントが復元して他人の Shopify customer に紐付くのを防ぐ)。
- **削除条件** (いずれかで即削除): ① redeem 成功 ② preview が `used` / `taken` / `expired` / `friend_conflict` を返した
  ③ 保存から 30 分経過 ④ ユーザーがカードを明示的に閉じた。
- 削除条件は**テストで固定**する (同一セッションでの再表示ループ防止も兼ねる)。

## 7. 60代の可読性 (実装トークン) — **Flex と LIFF の全 surface 共通**

### 7-1. コントラストは色名でなく閾値で規定する
> **白文字を載せてよいのは、白とのコントラスト比が 4.5:1 以上の背景だけ。**
> (相対輝度 L ≒ 0.15 以下は目安であって判定式ではない。**判定は常に比で行う** —

**到達 3/112 を突破した数少ない 60代が、最も読みづらいボタンで連携確定を迫られている。**

- `#0ABAB5` に白文字を載せない (約 2.5:1)。Flex の実行ボタン背景は **`#0f766e`** (**5.47:1**)。
- **`.btn-primary` の gradient を廃して solid `#0f766e` (5.47:1) にする** (または明るい側を `#1d7d82` 以上に暗くする)。

## 8. ブロック対策 (全 LINE 施策の死因)

### 8-1. 頻度制御の対象は marketing / 定期リマインドだけ
> **顧客自身の操作に対する応答 (受理・完了・failed・expired・実行漏れ検出・救済案内) は
> transactional。月 1 通の上限にも「止める」にも掛からない。**

これを書かないと、§4 で作った 3 層が opt-out 1 つで無音化する
(「休みにした」と信じたまま課金・出荷される)。判定基準は **「顧客の操作起点」または「法定通知」**。

### 8-2. reply と push を書き分ける (1 通に畳めない)
`executor='human'` の間、受理 (タップ直後) と完了 (スタッフ作業後・数時間〜翌営業日) は**必ず別イベント**。
畳むと完了通知が消え、顧客は状態確認のためポータルを開き直して**節約した以上のタップを払う**。

| 出来事 | 手段 | 頻度計上 |
|---|---|---|
| 受理「承りました (反映予定: ◯日)」 | **reply / LIFF 画面内表示** | 対象外 |
| 完了 `done` | **push (1 通)** | 対象外 (transactional) |
| 失敗 `failed` / 期限超過 `expired` / 実行漏れ検出 | **push (1 通・完了 push と排他)** | 対象外 (transactional) |
| 定期リマインド (7日前) | push | **月 1 通の枠** |
| 販促 | push | 月 1 通の枠 |

- 「受理通知と完了通知を 1 通に畳む」は**販促文脈の話ではない**ので、上表に置き換える。
- 約束破り通知 (§4-2) は **1 intent 1 回**に制限してブロック対策と両立させる。

### 8-3. 頻度セルフコントロール (LIFF の 1 画面)
提供面は **LIFF の 1 画面**。§7 のトークン・ボタン数規定を適用する。
ラベルは**対象語を必ず付ける** (同じカード群に §5 の pause / cancel が並ぶため、
「止める」だけだと定期便の停止・解約と読み違える):

```
[ お知らせは毎回ほしい ]
[ 大きな変更のときだけ ]
[ お知らせを止める (定期便は続きます) ]
```
- 3 択の直下に常時表示: **「決済失敗・発送・停止・お手続きの結果のお知らせは届きます」**

## 9. 却下した案と理由

| 却下 | 理由 |
|---|---|
| LINE ミニアプリ / Service Message | cron 起点は枠外・別トークルームで返信不可 = **相談導線が死ぬ**・1 アクション 5 通・push は既に無料枠内 |
| preview の friend 非依存化 | **死んだボタンが復活する退行**。`sub-link.ts` は preview と redeem の判定順序を一致させて「preview で ready を出したボタンが redeem で必ず失敗する」のを防いでいる。待ち時間は shimmer 先出しで消す |
| 聞かずに当てる引き止め | 稼働 84 契約 / 112 名という母数で行動推定に賭けるのは費用対効果が悪く、アンケートを後置すると**答え合わせが構造的にできない**。体に合わなかった人への誤爆ダメージが非対称 |
| 連携カードに通知 opt-in を既定 ON で同梱 | 友だち追加時点で受信可能なので実益が薄く**同意の質だけ下がる** |
| リマインドカードに `st=go` nonce を先出し | nonce TTL を数日に伸ばす必要があり、**古い吹き出しの後タップ面と攻撃面が既存設計より確実に広がる**。**ただし nonce を捨てる以上、代替の防壁 (§3-3 の `y`/`d0`/`v` サイクル束縛 + §1-1 の partial UNIQUE) は必須。07-24 設計の `L4 サイクル整合` を落とさないこと** |
| 「今回分だけ購入」の cart permalink + 割引コード | コードが LINE 履歴に残り**割引の外部流出経路**を作る |
